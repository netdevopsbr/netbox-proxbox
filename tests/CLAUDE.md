# `tests`

`test_openbao_credential_integration.py` pins conditional automatic storage,
explicit-choice precedence, required-secret failure and material validation, and
API authentication selection. `test_openbao_optionality_django.py` exercises real
Fernet round trips for all four endpoint secrets, the blank settings form and
serializer, forward migration preservation, and backend/export single-method
compatibility. It is enumerated in the real-Django workflow; the mocked suite
intentionally skips database assertions. Backend identity/transport tests use a
narrow storage-adapter stand-in; model validation explicitly reloads the real
adapter so transport stubs cannot suppress its checks.

The real optionality suite also covers endpoint-list serialization with missing,
deleted, and denied secrets; SSH reuse 422/503 responses; failed-then-healthy
monitoring scheduling; token-pair repairs; original-store preservation after
clears; actor propagation; and missing-address form errors. These caller tests
complement helper coverage and must remain in the native Django lane.

`test_proxmox_endpoint_allowed_tenants.py` keeps its source contracts in the
mocked suite and runs its database filter/serializer checks in the explicitly
enumerated real-Django matrix. Its fixture requires the active pytest-django
plugin, not merely importable modules: other mocked tests can leave Django
registry stubs in `sys.modules`. With `NETBOX_PROXBOX_REQUIRE_DJANGO=1`, a disabled

- `test_dependency_security_floors.py`: guards the declared dependency floors that carry a security meaning, which `uv.lock` cannot protect — the lock is neither shipped in the wheel nor consulted by `pip`, so a floor admitting an advisory-covered version silently re-introduces the vulnerability on the next fresh resolve while the lockfile scanner reports nothing. Each `SECURITY_FLOORS` entry names the manifest positions that must declare it (`declared_in`), and every one is checked: `aiohttp` in the shipped `cli` extra and `requirements-docs.txt`; `pymdown-extensions` in `[dependency-groups].dev` and `requirements-docs.txt`. `pymdown-extensions` is only ever *transitive* — `mkdocs-material` asks merely for `>=10.2`, which admits both GHSA-gm37-52c6-37mw (`<=11.0.0`) and GHSA-9xwg-3r6f-jcx2 (`<=10.21.3`) — and `.github/workflows/docs.yml` installs the docs requirements with a plain `pip install -r` that reads no lockfile, so an **undeclared** package is a real exposure and the guard treats "not declared here" as a failure rather than a skip. The lock test pins the inverse mistake: a declared floor raised while `uv.lock` stays below it, which makes `uv sync --locked` inconsistent.

  **The safety assertion is structural, not a sample, and that distinction is the whole point.** An earlier version only asserted that a handful of enumerated affected versions were refused, and an adversarial review broke it by *execution*: `aiohttp>=3.13.0,!=3.14.0,!=3.14.1,!=3.14.2` refuses every sampled version, admits the patched floor, and still admits the advisory-covered 3.13.5 — so the guard passed a vulnerable manifest. `_effective_lower_bound()` now requires the specifier to *establish* a lower bound at or above the floor, and `!=` clauses deliberately do not count as one, because excluding known-bad versions one at a time is exactly the bypass. That predicate is unit-tested directly as a 12-case table (`>=`/`==`/`===`/`~=`/wildcard/multiple-ANDed-bounds, plus the exclusion-only, upper-bound-only, and empty cases returning `None`), and the demonstrated bypass has its own named regression test asserting both that it dodges the sample oracle and that the structural check rejects it. The sampled-version check is kept alongside it only because it names a real affected version in its failure message.

  There is deliberately **no** "the two manifests declare identical specifiers" test: the historical drift (`>=3.14.1` in the extra versus `>=3.12.15` in the docs requirements) is caught better by checking each manifest independently against the same fixed matrix, since raising `SECURITY_FLOORS` fails *every* affected manifest check until *every* file is bumped — whereas a string comparison also rejects safe, legitimate differences (`==3.14.5` or `~=3.14.3` against `>=3.14.3`), and a guard that fires on safe input creates pressure to weaken it.

  **An environment marker is validated, not merely tolerated** — an earlier revision claimed markers were "handled" while in fact ignoring them, and a review broke it by reproduction: `pymdown-extensions>=11.0.1; python_version < "3"` parses fine and yields a lower bound of 11.0.1, so both assertions passed, yet the marker is false on every supported interpreter — the floor was inert and `mkdocs-material`'s weaker `>=10.2` governed. `_inactive_environment()` now requires a marker to hold across **every** supported environment and reports the first counterexample otherwise, so a platform-conditional floor (`; sys_platform == "linux"`) or one that lapses on a future interpreter (`; python_version < "3.14"`) is rejected while a genuinely unconditional one is accepted. The environment matrix is **derived from `requires-python`** (its lower bound plus three minor versions, crossed with the platform axes) rather than hardcoded, so it cannot drift out of step with the project's own floor — lowering `requires-python` widens the matrix automatically, and a missing `requires-python` fails closed. The predicate has its own 8-case table, whose always-true rows deliberately use matrix-independent markers so the table tests the predicate instead of quietly becoming a second assertion about the Python floor.

  Other real pip requirement-file syntax is handled rather than assumed: trailing comments, extras, and `==`/`~=` pins judged on the version they admit, joined backslash continuations, and pip *options* such as `--index-url` ignored because they declare no requirement. Directives the line parser cannot see through are a **hard failure**: `-r`/`-c`/`--requirement`/`--constraint` pull in whole files, and `-e`/`--editable` is itself an install requirement, so an editable VCS reference to an affected version would otherwise be skipped silently. Two design constraints are deliberate and must not be relaxed. **The oracle is a fixed matrix** (`SECURITY_FLOORS`) transcribed once from the published advisories and naming concrete versions that MUST be rejected, so the assertions cannot be satisfied by whatever the manifest happens to say — a test that derived the expected floor from the manifest would assert only that the code agrees with itself. **Manifests are parsed with `tomllib` + `packaging`, never a whole-file regex**, because a regex scanning the whole document can match a decoy in an unrelated table and report a floor that is not the one in force; a false floor is worse than no guard, because it reports success. Every check **fails closed**: a missing file, unparseable manifest, absent table, absent dependency, or duplicate declaration is a FAILURE, never a `pytest.skip` — skipping is reserved for a property that legitimately does not apply (the manifest simply does not install the package), never for an inability to evaluate one. Mutation-tested in both directions: reverting either floor or the lock pin goes red, and so does deleting/emptying/corrupting any input or removing the dependency entirely, while a decoy low floor added to an unrelated extra correctly does **not** change the verdict. `cryptography` is deliberately absent from the matrix — its advisory covers `>=44.0.0, <50.0.0` so `cryptography>=48.0.1` does admit affected versions, but this project's only surface is `Fernet`/`InvalidToken`, which the PKCS#7 `EnvelopedData` defect does not touch, and raising a *runtime* floor forces an upgrade inside the production NetBox virtualenv on deploy; that trade-off is tracked separately rather than silently enforced here.

The recording end has its own Proxmox twins — `test_recording_a_pushed_proxmox_fingerprint_updates_the_row_without_saving_it` and `…_survives_an_unapplied_migration` — mirroring the NetBox pair (write through `queryset.update()`, never `save()`; a missing 0074 column degrades to always-push instead of failing the push), plus `test_proxmox_and_netbox_credential_fingerprints_never_compare_equal`, which feeds both fingerprint functions identical material and pins that the distinct salts keep the two namespaces disjoint. `test_run_scopes_firewall_and_datacenter_to_the_runs_endpoints` pins that `run()` forwards `endpoint_ids_to_sync` to the firewall and datacenter passes, which used to build their own all-enabled scope and ignore the job's selection. They also share `_preflight_proxmox_endpoint(pk)` / `_arrange_slow_push(..., held=…)`, which build **complete, current** backend rows rather than bare `{"name": …}` stubs — `backend_holds_proxmox_endpoint()` now means "held *and* current", so a row missing `port`/`username`/`access_methods`/`verify_ssl` reads as drifted and the budget correctly refuses to skip it, which is not the behavior those three tests are about. A further group pins the **backend-pin round trip** that keeps a *replayed* job on the same proxbox-api: `enqueue()` persists `fastapi_endpoint_id` into `job.data['proxbox_sync']['params']` (coercing `"7"` → `7` and dropping an unusable value entirely rather than storing a half-parsed pk), still forwards the kwarg to `run()`, omits the key when unpinned, and `proxbox_sync_params_from_job()` reads it back on **both** return paths — including the legacy targeted-VM name inference, which rebuilds the params from scratch. `_coerce_fastapi_endpoint_id` is parametrized directly, `True`/`False` included (a `bool` is an `int` in Python and must not become endpoint 1). Two further tests pin that the coercion happens **before** `super().enqueue()` and **again** at the top of `run()`, which is what keeps the queued RQ kwargs and `job.data` from disagreeing: `test_enqueue_never_queues_a_pin_it_refused_to_store` asserts an unusable pin appears in *neither*, and `test_run_recoerces_an_unusable_backend_pin_before_any_lookup` asserts `run()` normalises it before the preflight sees it (direct callers, and RQ payloads queued by a release predating the `enqueue()` coercion, still hand it a raw value). `True` is the sharp case both ways — it survives every guard and Django resolves `pk=True` against primary key 1. A further group pins that **a stored backend row is only trusted once it is identified**: a failed push plus a row whose **resolved connection target** — `(domain or ip_address)` plus `port` — equals this NetBox's warns "may be stale" and continues, while a row with the *same name* but a different target, the right host on a different port, a *different* domain sharing our configured IP, a blank domain at our IP while we declare one, a row reporting no port at all, or nothing but the synthetic `127.0.0.1` push fallback all block with "do not point at this NetBox". Matching by name would pass the first — the backend NetBox endpoint is a singleton updated by position and its payload name is free text. **That positional singleton is itself asserted**: `test_preflight_blocks_when_only_a_later_backend_row_is_ours` feeds a two-row listing whose *second* row is ours and pins that the run blocks anyway, with no "may … stale" warning, because a match at index 1 vouches for a row proxbox-api is not dialling while the stale row at index 0 drives the sync. `test_preflight_continues_when_backend_already_holds_an_endpoint` therefore feeds the *single* row it always claimed to. Two tests deliberately feed the *same* stored row to opposite verdicts: reached-by-address blocks a domain-configured NetBox and continues an IP-only one, because which field the backend dials is what decides identity. Two more pin fix N, that **"unknown" must not read as "ours"**: a failed push whose backend listing *also* failed blocks, unless some other enabled row pushed successfully (that push already wrote this NetBox's credentials into the singleton, so the unreadable listing has nothing left to add). **These tests call the real `backend_holds_netbox_endpoint()` / `backend_holds_proxmox_endpoint()`, installed on the fixture's fake module by `load_real_backend_sync()` — never a hand-written mirror.** That is not a style preference. The fixture used to re-implement the predicate "faithfully", and when the real helper was found to match two different domain-only NetBoxes against each other through the loopback fallback, every test still passed, because they were asserting against the copy. The defect survived six adversarial review rounds that way. `load_real_backend_sync()` path-loads `views/backend_sync.py` once against throwaway stubs (saving and restoring the eight `sys.modules` entries in a `try/finally`) and takes only the pure predicates; everything that performs HTTP is stubbed separately, so nothing there can reach the network. `test_backend_holds_netbox_endpoint_identity_contract` then states the contract directly as a 21-case table against that same real function, in five groups — positive identification, the loopback trap, a different resolved connection target, the port, and the fail-closed inputs — because the `run()`-level tests only exercise one verdict each. The fail-closed group is where the **positional singleton** is pinned: a single junk entry is `False` without raising, and *any* listing longer than one row is `False` too — including two of **our own** rows, and junk followed by ours — because the push overwrites entry `[0]` and entry `[0]` is what the backend dials, so a longer list means nothing in the response says which row wins. The table is what pins the two directions a field-by-field comparison gets wrong: a stored row blank on `domain` at our IP, or naming *another* domain at our IP, must **not** match (both dial a different service at that address), while our own row whose stored IP has since drifted **must** still match, because a row with a domain never dials its address at all. Its rows are built by `_stored_row()`, which supplies a *current* `verify_ssl`/`token_version` by default, because identity and **currency** are separate questions and that table is only asking the first one. `test_backend_holds_netbox_endpoint_currency_contract` asks the second as its own 10-case table: a `verify_ssl` or `token_version` that drifted in **either** direction is refused, whitespace-only differences are not, an *absent* `verify_ssl` or `token_version` reads as drifted (a `False` here blocks the run, so unknown must fail closed), and **currency is only ever asked of the row the backend dials** — a current duplicate sitting *behind* a drifted row does not rescue it, and neither does a current row belonging to a *different* NetBox, both now twice over since a listing longer than the positional singleton is refused before currency is asked at all. Three preflight-level tests take it end to end — a superseded TLS posture, a superseded token scheme, and a row omitting a mandatory trust field all block the run rather than warning and continuing. Four more pin the **secret** the currency check structurally cannot see, because `NetBoxEndpointResponse` withholds `token`/`token_key`: `test_preflight_blocks_when_the_stored_row_predates_an_in_place_token_rotation` (identity says "ours" and currency says "current", both correctly — and the run would still proceed on a revoked token, so the locally recorded fingerprint of the last **successful** push is the only thing left that can tell), `test_preflight_blocks_when_no_push_ever_recorded_a_credential_fingerprint` (an *empty* fingerprint reads as drifted, because unknown must fail closed; one successful push clears it permanently), and two on the writer itself — `test_recording_a_pushed_fingerprint_updates_the_row_without_saving_it` asserts it goes through `type(endpoint).objects.filter(pk=pk).update(...)` and **never** `save()`, since `NetBoxEndpoint`'s `post_save` handler re-pushes to the backend and saving from inside a push would recurse, while `test_recording_a_pushed_fingerprint_survives_an_unapplied_migration` feeds it the `ProgrammingError` an install without migration `0073` raises and asserts the push still succeeds with the fingerprint left empty (i.e. fail-closed, not fail-loud). `_arrange_preflight(..., netbox_fingerprint="current"|"stale"|"absent")` selects the three states, computing `"current"`/`"stale"` through the **real** `netbox_endpoint_credential_fingerprint()` rather than a literal — `salted_hmac` is implemented faithfully in `tests/django_stubs.py` for exactly this reason, since stubbing it to a constant would make every fingerprint compare equal and silently delete the test. Four more pin the **selected-object batch path**: it blocks with zero enabled `NetBoxEndpoint` rows and never calls `_run_batch_selected_sync` (it used to return *before* the preflight entirely), it forwards the job's `fastapi_endpoint_id` into that call, `_run_batch_selected_sync` itself passes the id to every per-object `sync_individual_with_dependencies`, and — via `_arrange_batch_storage_sync()`, shared by the last two so both assert the **whole** call dict rather than one key — it passes `netbox_branch_schema_id` as a keyword and not only inside `query_params`. ## Notes

- Tests rely heavily on compatibility stubs in `conftest.py` rather than a live NetBox database.
- When changing view, job-enqueue, or template contracts, update both the runtime code and those stubs.
- `test_frontend_contracts.py` guards against accidental regressions in public-facing attribute names and JS function signatures.
- **Wire-contract tests:** `test_sse_schema_mirror.py` validates local REST/SSE schema mirrors against `contracts/proxbox_api_sse_schema.json`. It must not import or install `proxbox-api`; the plugin and backend communicate over HTTP, not direct Python calls.
- **AST-based source contracts** (e.g. `test_version.py`, `test_signals.py`, `test_services_backend_context.py`, `test_proxmox_endpoint_settings_view.py`, `test_views_vm_config.py`, `test_views_storage.py`) parse the relevant module with `ast` and never bootstrap Django. Use this pattern when the runtime cost of starting NetBox would dominate the test value. When such a test needs a module's constant values, read them with `ast.literal_eval` — never `eval()`, which the workspace security hook rejects outright.

### Stub-loader constraints

Tests that load a plugin module by file path (`spec_from_file_location` +
`monkeypatch.setitem(sys.modules, ...)`) run it against hand-built stub modules
rather than real NetBox. Two failure modes are easy to hit and hard to read:

- **No `@dataclasses.dataclass` in a module that uses `from __future__ import
  annotations`.** Under Python 3.14, `dataclasses._is_type` resolves string
  annotations through `sys.modules[cls.__module__]`, which is `None` for a
  path-loaded module the loader never registered — so the decorator raises
  during import, far from the actual test. `jobs.py`'s `PreflightResult` is a
  plain class with `__slots__` for exactly this reason.
- **Stub the whole `netbox_proxbox.services` package, not individual
  submodules.** `jobs.py` imports `netbox_proxbox.services.branch_lifecycle`
  lazily inside `run()`, guarded only by `except ModuleNotFoundError`. A partial
  stub lets the real `services/__init__.py` execute, which drags in
  `backend_proxy.py` and raises a chain of `ImportError`s — a *different*
  exception class, so the guard does not catch it and the test fails on an
  unrelated import. `monkeypatch.setitem(sys.modules,
  "netbox_proxbox.services", services_mod)` is the established idiom; see the
  `run()`-level tests in `test_jobs.py`.
- **A new `from netbox_proxbox.sync_params import …` name must be added to the
  stub in `test_service_monitoring_scheduler.py`.** That test installs a
  hand-built `netbox_proxbox.sync_params` module listing each symbol `jobs.py`
  imports; a name missing from that list fails at *import* time with
  `ImportError: cannot import name … (unknown location)`, in a test that has
  nothing to do with the change.
- **The `proxbox_sync_job_module` fixture models a *normal* deployment: one
  enabled Proxmox endpoint that resolves to a backend wire id.** Its
  `_EndpointManager.filter()` synthesizes rows on demand — per requested pk for a
  `pk__in`/`pk` lookup, and a single default endpoint (pk 1) for an *unfiltered*
  `filter(enabled=True)` — and the fixture installs a default
  `sync_stages._resolve_wire_endpoint_ids` that maps each scoped pk to itself.
  Both defaults are load-bearing: without them every `run()`-level test lands in
  the "no enabled Proxmox endpoint" / "never resolved to a backend id" fail-loud
  branches, exercising a disabled-estate path none of them meant to test, and the
  failure surfaces as ~19 unrelated tests breaking at once. A test that wants the
  empty estate must override `models.ProxmoxEndpoint` itself (see
  `test_proxmox_endpoint_scopes_returns_no_scope_when_every_endpoint_disabled`);
  a test that wants a resolution failure re-patches `_resolve_wire_endpoint_ids`,
  which wins because test bodies run after the fixture.
- **Load a security predicate, never mirror it.** When a stubbed module needs a
  helper that decides *whether an operation may proceed* — as opposed to one
  that merely performs I/O — install the real function via a path-loader instead
  of re-implementing it on the fake module. `test_jobs.py`'s
  `load_real_backend_sync()` is the pattern: stub `netbox_proxbox`,
  `.models`, `.utils`, `.services`, `.services.endpoint_enabled`, `.views`, and
  `.views.error_utils`, `spec_from_file_location` the target, then restore every
  saved `sys.modules` entry in a `finally`. A mirror silently stops testing the
  thing it names the moment the real code changes, and the tests keep passing
  while it does.
- **Coverage:** `pyproject.toml` defines `[tool.coverage.run]` with `source = ["netbox_proxbox"]` and `branch = true`, plus `[tool.coverage.report]` with `exclude_lines` for `TYPE_CHECKING` and `pragma: no cover` markers. Mocked CI invokes `pytest --cov=netbox_proxbox`; the real-Django matrix explicitly measures both `services.endpoint_autoconfiguration` and `api.serializers.resource_views` with branch coverage and an 85% floor so bridge-v1 serializer validation cannot remain unmeasured.
